感谢你帮助改进 Koharu。无论规模大小，我们都欢迎缺陷修复、文档、翻译、模型移植修正，以及范围明确的产品改进。

## 找到适合参与的工作

- 浏览 [good first issues](https://github.com/koharu-rs/koharu/contribute)。
- 搜索相关的[现有 Issue](https://github.com/koharu-rs/koharu/issues) 与 PR。
- 如果需要帮助选择 Issue 或缩小范围，可以在 [Discord](https://discord.gg/mHvHkxGnUY) 中交流。

## 规划修改

明确的缺陷修复、文档改进、测试和其他范围集中的修改通常可以直接提交。每个 PR 请专注于一个问题。

在实现新产品功能、重要 UI 修改、新模型或服务商、平台集成、依赖项、公共 API、模式变更或架构重构之前，请先创建 Issue，与维护者讨论问题和建议方向。我们希望尽早讨论想法，避免你花费时间实现 Koharu 无法持续维护的工作。

现有 Issue、功能请求或已完成的实现并不代表修改一定会被接受。即使已就方向达成一致，也不保证每种实现都会被合并。

受影响 crate 的 README 可以帮助你了解该组件的职责。

## 功能评估方式

维护者会考虑：

- 是否符合 Koharu 的产品方向；
- 对用户的价值，以及使用场景是否足够广泛；
- 对 UX、架构、性能、安全、隐私和平台支持的影响；
- 测试、文档、依赖项和运维复杂度；
- 维护者能否长期支持该功能。

维护者可能会拒绝或推迟某项功能、要求缩小范围、采用其他设计，或建议在核心项目之外维护。这并不是对提案所投入精力的否定。

修改合并后，其维护工作将由项目负责。贡献者愿意继续提供帮助非常宝贵，但即使贡献者之后无法继续参与，Koharu 仍必须能够接手并维护该功能。

## 遵循 Koharu 的项目规则

- API 或架构变化时，更新仓库内所有使用方，不添加兼容别名。
- 服务商专用默认值和请求行为由对应服务模块拥有。
- 将安全公共 API 与 unsafe FFI、动态加载分离。
- 移植上游模型时，保留影响检查点的结构，并在相同输入上比较结构化输出。
- 在实际目标设备上使用代表性输入测量性能，同时报告速度与正确性。
- 不要提交凭据、模型权重、数据集、生成输出、构建产物或机器特有文件。

注释最适合用于解释所有权、不变量、上游映射或有意差异。

## 检查修改

请审查完整差异，并运行与修改对应的最小 debug 检查或聚焦测试一次，不必运行无关的完整测试套件。格式化修改过的 Rust 和 TypeScript 文件，并运行 `git diff --check`。

根据修改内容，在适用时提供以下证据：

- 可见 UI 修改的截图；
- 性能工作的设备、输入、基准、结果和正确性差异；
- 模型移植的结构化输出比较。

如果受环境限制而无法运行某项检查，请在 PR 中说明，让审查者清楚哪些内容尚未验证。

## 创建 PR

请说明问题、选择的解决方案、重要的行为或所有权边界变化，以及执行过的检查。不要在同一个 PR 中加入无关重构，以便保持修改易于审查。

审查是一个沟通过程。维护者可能会建议修改或缩小范围；如果反馈不清楚，欢迎随时提问。

## AI 辅助贡献

AI 工具可以辅助开发或沟通，但每项提交都必须由一位真实的贡献者作为作者并承担责任。

如果 AI 对修改的设计或实现提供了实质性帮助，请在 PR 描述中说明帮助的范围和目的。常规代码补全、语法修改和翻译不需要详细披露。

请勿提交由自主代理创建或发布，或未经人工审查的 Issue、PR、审查评论或安全报告。提交前，你必须：

- 亲自审查完整差异；
- 根据代码核实生成的说法，并复现所报告的问题；
- 理解并能够说明每项修改及其重要边界情况；
- 能够根据审查意见修改实现；
- 提供与其他贡献相同标准的相关测试和验证依据。

请将生成内容视为草稿，而不是证据或完成的贡献。PR 描述和对维护者的回复必须反映你自己的理解。

如果提交内容看起来未经人工审查、包含推测或虚构的说法、贡献者无法说明或修改，或其审查成本明显高于带来的价值，维护者可以不进行详细审查而直接关闭。如果不确定使用 AI 工具的方式是否合适，请在提交前询问。
