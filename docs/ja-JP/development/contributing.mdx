Koharu の改善にご協力いただきありがとうございます。バグ修正、ドキュメント、翻訳、モデル移植の修正、範囲を絞った製品改善など、規模を問わず歓迎します。

## 貢献する内容を探す

- [good first issues](https://github.com/koharu-rs/koharu/contribute) を確認します。
- 関連する [Issue](https://github.com/koharu-rs/koharu/issues) と PR を検索します。
- Issue 選びや範囲の絞り方に迷ったら [Discord](https://discord.gg/mHvHkxGnUY) で相談してください。

## 変更を計画する

明確なバグ修正、ドキュメント改善、テスト、その他の範囲を絞った変更は、通常そのまま PR として提出できます。1 つの PR では 1 つの問題に集中してください。

新しい製品機能、重要な UI 変更、新しいモデルやプロバイダー、プラットフォーム統合、依存関係、公開 API、スキーマ変更、アーキテクチャのリファクタリングを実装する前に Issue を作成し、問題と提案する方針をメンテナーと相談してください。Koharu が継続して維持できない作業に時間を費やしていただくよりも、早い段階でアイデアを相談したいと考えています。

Issue や機能要望が公開されていること、または実装が完成していることは、その変更の受け入れを約束するものではありません。方針に合意していても、すべての実装がマージされるとは限りません。

変更対象クレートの README は、そのコンポーネントの責任を理解するための参考になります。

## 機能提案の判断基準

メンテナーは次の点を考慮します。

- Koharu の製品方針に沿っているか
- 利用者にとって価値があり、十分に広いユースケースがあるか
- UX、アーキテクチャ、性能、セキュリティ、プライバシー、プラットフォーム対応への影響
- テスト、ドキュメント、依存関係、運用上の複雑さ
- メンテナーがその機能を長期的にサポートできるか

メンテナーは、機能を見送ったり延期したり、範囲の縮小や別の設計を求めたり、コアプロジェクトの外で維持することを提案したりする場合があります。これは、提案に費やされた努力を否定するものではありません。

変更がマージされると、その保守はプロジェクトの責任になります。コントリビューターが継続して協力する意思は有益ですが、その協力が難しくなった場合でも Koharu が機能を所有できる必要があります。

## Koharu のプロジェクトルールに従う

- API やスキーマを変えたら、互換エイリアスを追加せず、リポジトリ内の全利用側を更新します。
- プロバイダー固有の既定値と要求変換は、そのプロバイダーに置きます。
- 安全な公開 API と unsafe FFI・動的ロードを分離します。
- 上流モデル移植ではチェックポイントに影響する構造を保ち、同一入力の構造化出力を比較します。
- 性能変更は実際の対象デバイスと代表入力で測定し、速度と正しさの両方を報告します。
- 認証情報、モデル重み、データセット、生成物、ビルド出力、端末固有ファイルをコミットしません。

コメントは、所有、制約、上流との対応、意図的な差分を説明するときに特に役立ちます。

## 変更を確認する

差分全体をレビューし、変更に最小限必要な debug プロファイルのチェックまたはテストを 1 回実行します。無関係なフルテストスイートは不要です。変更した Rust と TypeScript ファイルを整形し、`git diff --check` を実行してください。

変更内容に応じて、次の確認結果も含めます。

- UI の見た目を変えた場合のスクリーンショット
- 性能変更のデバイス、入力、基準、結果、正しさの差分
- モデル移植における構造化出力の比較

環境上の理由で実行できない確認がある場合は、未検証の内容が分かるよう PR に記載してください。

## PR を作成する

問題、選んだ解決方法、重要な挙動や所有境界の変更、実行した確認を説明してください。レビューしやすいよう、無関係なリファクタリングは同じ PR に含めません。

レビューは対話です。メンテナーが修正や範囲の縮小を提案することがあります。フィードバックが分かりにくい場合は、遠慮なく質問してください。

## 生成 AI を利用した貢献

生成 AI ツールは開発やコミュニケーションの支援に利用できますが、すべての提出物には人間の作成者と責任者が必要です。

AI が変更の設計や実装を実質的に支援した場合は、PR の説明に支援の範囲と目的を記載してください。通常のコード補完、文法修正、翻訳について詳しい開示は不要です。

自律的に作成・投稿されたもの、または人間がレビューしていない Issue、PR、レビューコメント、セキュリティ報告は提出しないでください。提出前に、次のことを行う必要があります。

- 差分全体を自分でレビューする
- 生成された主張をコードと照合し、報告する問題を再現する
- すべての変更と重要なエッジケースを理解し、説明できるようにする
- レビューに応じて実装を修正できるようにする
- 他の貢献と同じ水準のテストと確認結果を提供する

生成された出力は、根拠や完成した貢献ではなく下書きとして扱ってください。PR の説明とメンテナーへの回答の内容には、提出者自身の理解が反映されている必要があります。

人間によるレビューが行われていない、推測や架空の主張を含む、提出者が説明や修正をできない、または得られる価値に対して著しく大きなレビュー負担を要する場合、メンテナーは詳細なレビューを行わずに提出をクローズすることがあります。AI ツールの利用方法が適切か迷う場合は、提出前に相談してください。
