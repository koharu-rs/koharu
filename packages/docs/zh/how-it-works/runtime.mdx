所有模型都在一块 GPU 上运行：本机最好的那一块。Koharu 在首次需要时下载该 GPU 所需的库和每个模型的权重并保留下来，此后直接从磁盘运行。

## 一块 GPU

模型共享一块 GPU 的内存。如果分散到多块 GPU，模型能否放下就会取决于谁先运行，因此首次运行模型时，Koharu 会选定一块 GPU，并在本次会话中一直使用它：

| 顺序 | GPU                        |
| ---- | -------------------------- |
| 1    | Metal，或独立 NVIDIA GPU   |
| 2    | 独立 AMD GPU               |
| 3    | 集成 NVIDIA GPU            |
| 4    | 集成 AMD GPU               |
| 5    | 通过 Vulkan 使用的其他 GPU |

同一顺序中，显存更大的优先，其次是更新的 CUDA 架构。如果最好的 GPU 无法使用，任务会失败，而不会改用下一块，因此模型不会在你意料之外的设备上运行。没有纯 CPU 模式。

运行检测、OCR 和 LaMa 的 libtorch 没有 Vulkan 版本，因此在 Vulkan 机器上这三者在 CPU 上运行。语言模型和扩散类修补模型在 Vulkan GPU 上运行。

## 会下载什么

| 软件包                    | 来源                                | 用途             |
| ------------------------- | ----------------------------------- | ---------------- |
| CUDA                      | PyPI 上的 NVIDIA 软件包             | NVIDIA GPU       |
| ROCm                      | AMD 的软件包                        | AMD GPU          |
| libtorch 及 Koharu 的绑定 | GitHub 上 Koharu 自己的构建         | 所有 GPU         |
| llama.cpp                 | GitHub 上 Koharu 自己的构建         | 所有 GPU         |
| stable-diffusion.cpp      | GitHub 上 Koharu 自己的构建         | 所有 GPU         |
| 模型权重                  | Hugging Face，固定到某个提交        | 各个模型         |
| 字体                      | Hugging Face 上的 Koharu 字体数据集 | 需要该字面的文字 |

- **固定版本。** 每个软件包和模型都固定到一个版本，因此同类机器上的模型运行在相同的库构建上。
- **全有或全无。** 所有库下载完成后才会打开，因此下载失败不会留下加载了一半的东西。
- **不留半成品。** 下载先写入同一磁盘上的暂存文件夹，校验后再移到最终位置。锁可防止另一个 Koharu 同时下载同一内容。
- **重试。** 服务器允许时，库软件包会通过多个连接下载，每个连接都会重试几次。中途断开的模型文件会从头重新下载。
- **清理。** 启动加载完库后，旧版本会在后台删除。模型文件会保留。

所有内容都放在同一个存储中，位置参见[数据位置](/zh/reference/data#运行时与模型存储)。

## 内存

模型在某个阶段首次需要时加载，并为之后的任务保持加载。模型在负责它们的线程上逐个加载，因此每次加载看到的都是实际的可用内存。

- **不会为腾出空间而卸载。** 放不下的模型会失败，错误信息会给出可用内存。请选择更小的模型，把其他阶段换成更轻的模型，或选择**编辑 → 卸载模型**释放 Koharu 加载的所有模型。
- **模型在以下情况下移出**：设置切换到其他模型、你卸载模型，或 Koharu 退出。设置中未使用的创成式填充模型会在最后一次填充五分钟后移出。
- **本地语言模型**会缩小上下文、把部分层移到系统内存以放得下。扩散类修补模型会先把权重放进 GPU 的可用内存，不够时再放进系统内存。

能放进磁盘的模型，仍可能超出 GPU 内存。更小的模型和量化需要的内存更少，但通常会牺牲一些质量。

## 轮流使用 GPU

图像类模型一次只执行一个调用，因此内存峰值是所有已加载模型加上最大的单个作业，内存是否耗尽不会取决于时机。本地语言模型在旁边自己的线程上生成。

在 CUDA 上，llama.cpp 会把它的工作捕获为图，而其他库等待整个 GPU 的调用会破坏这种捕获。因此在 CUDA 上 llama.cpp 和 stable-diffusion.cpp 轮流使用 GPU，在 ROCm 上 libtorch 也加入轮流。正在执行长作业的库，在有其他库等待时会在五秒后让出 GPU。在 Metal 和 Vulkan 上，它们并行运行。

## 任务如何排序

- **交互优先。** 针对文本块或涂抹区域的任务，会在下一次模型调用时排到针对页面的任务之前，因此**移除**笔画不必等整章处理完。针对页面的任务按到达顺序进行。
- **同时处理三页。** 一页在读取输入，一页在模型上运行，一页在写入结果。
- **页内顺序。** 检测先于该页的其他阶段，OCR 先于该页的翻译；翻译是一段对话，因此每页的翻译先于下一页的翻译。
- **批处理。** OCR 会把等待中的页面最多 8 页合并为一批读取。
- **停止。** **停止**会结束所有正在运行和排队的任务，并中断扩散模型正在进行的重绘。停止的任务不会再写入任何内容。
