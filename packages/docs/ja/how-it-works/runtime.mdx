すべてのモデルは 1 つの GPU、つまりそのマシンで最も良い GPU で動きます。Koharu はその GPU に必要なライブラリと各モデルの重みを、初めて必要になったときにダウンロードして保持し、以後はディスクから動かします。

## 1 つの GPU

モデルは 1 つの GPU のメモリを分け合います。複数の GPU に分けると、モデルが収まるかどうかがどれが先に動いたかで変わってしまうため、Koharu はモデルが初めて動くときに GPU を 1 つ選び、そのセッションの間使い続けます。

| 順位 | GPU                              |
| ---- | -------------------------------- |
| 1    | Metal、または独立型の NVIDIA GPU |
| 2    | 独立型の AMD GPU                 |
| 3    | 内蔵の NVIDIA GPU                |
| 4    | 内蔵の AMD GPU                   |
| 5    | Vulkan で使えるその他の GPU      |

同じ順位ではメモリが多いほう、次に新しい CUDA アーキテクチャが優先されます。最も良い GPU が使えない場合は、次の GPU に切り替えずに実行が失敗するため、モデルが思わぬ場所で動くことはありません。CPU だけで動くモードはありません。

検出、OCR、LaMa を動かす libtorch には Vulkan 版がないため、Vulkan のマシンではこの 3 つは CPU で動きます。言語モデルと拡散系のインペイントモデルは Vulkan の GPU で動きます。

## ダウンロードされるもの

| パッケージ                          | 取得元                                          | 用途                     |
| ----------------------------------- | ----------------------------------------------- | ------------------------ |
| CUDA                                | PyPI 上の NVIDIA のパッケージ                   | NVIDIA GPU               |
| ROCm                                | AMD のパッケージ                                | AMD GPU                  |
| libtorch と Koharu のバインディング | GitHub 上の Koharu 自身のビルド                 | すべての GPU             |
| llama.cpp                           | GitHub 上の Koharu 自身のビルド                 | すべての GPU             |
| stable-diffusion.cpp                | GitHub 上の Koharu 自身のビルド                 | すべての GPU             |
| モデルの重み                        | Hugging Face（固定したコミット）                | 各モデル                 |
| フォント                            | Hugging Face 上の Koharu のフォントデータセット | 書体を必要とするテキスト |

- **固定。** すべてのパッケージとモデルは 1 つのバージョンに固定されるため、同じ種類のマシンではモデルが同じライブラリのビルドで動きます。
- **すべてか、何もないか。** どのライブラリも、すべてのダウンロードが終わるまで開かれないため、ダウンロードに失敗しても中途半端に読み込まれたものは残りません。
- **書きかけを残さない。** ダウンロードは同じディスクの一時フォルダーに書き込まれ、確認されてから所定の場所に移されます。ロックにより、別の Koharu が同じものを同時にダウンロードすることはありません。
- **再試行。** ライブラリのパッケージは、サーバーが許せば複数の接続でダウンロードされ、それぞれ数回再試行されます。途中で切れたモデルファイルは最初からやり直します。
- **片付け。** 起動時にライブラリを読み込んだ後、古いバージョンはバックグラウンドで削除されます。モデルファイルは残ります。

すべては 1 つのストアに入ります。場所は[データの保存場所](/ja/reference/data#ランタイムとモデルのストア)を参照してください。

## メモリ

モデルは工程が初めて必要としたときに読み込まれ、以後の実行のために読み込まれたままになります。モデルはそれを担うスレッドで 1 つずつ読み込まれるため、各読み込みは実際の空きメモリを見ます。

- **場所を空けるためにアンロードはしません。** 収まらないモデルは失敗し、エラーに空きメモリが示されます。小さいモデルを選ぶか、ほかの工程を軽いモデルに切り替えるか、Koharu が読み込んだすべてのモデルを解放する**編集 → モデルをアンロード**を選んでください。
- **モデルが外れるのは**、設定でほかのモデルに切り替えたとき、モデルをアンロードしたとき、Koharu を終了したときです。設定で使っていない生成塗りつぶし用のモデルは、最後の塗りつぶしから 5 分後に外れます。
- **ローカルの言語モデル**は、収まるようにコンテキストを縮め、レイヤーをシステムメモリへ移します。拡散系のインペイントモデルは、重みを GPU の空きメモリに置き、足りなければシステムメモリに置きます。

ディスクに収まるモデルでも、GPU のメモリを超えることがあります。小さいモデルや量子化はメモリが少なくて済みますが、たいてい品質は下がります。

## GPU を順番に使う

画像系のモデルは一度に 1 回ずつ呼び出されるため、メモリ使用量の最大値は、読み込んだすべてのモデルと最大の 1 つの処理の合計になり、メモリ不足が実行のタイミングで左右されることはありません。ローカルの言語モデルは、その横の専用スレッドで生成します。

CUDA では llama.cpp が処理をグラフとして記録しますが、ほかのライブラリが GPU 全体を待つ呼び出しをするとこれが壊れます。そのため CUDA では llama.cpp と stable-diffusion.cpp が順番に GPU を使い、ROCm では libtorch も順番に加わります。長い処理の途中のライブラリは、ほかが待っていれば 5 秒後に GPU を譲ります。Metal と Vulkan では並んで動きます。

## 実行の順序

- **対話的な実行が先。** テキストブロックや塗った範囲への実行は、次のモデル呼び出しの時点でページへの実行より先に進むため、**削除**のストロークが章全体の処理を待つことはありません。ページへの実行は来た順に進みます。
- **同時に 3 ページ。** 1 ページが入力を読み、1 ページがモデルにかかり、1 ページが結果を書き込みます。
- **ページ内の順序。** 検出はそのページのほかの工程より先、OCR はそのページの翻訳より先に行われます。翻訳は 1 つの会話なので、各ページの翻訳は次のページの翻訳より先に行われます。
- **まとめて処理。** OCR は待っているページを最大 8 ページまとめて読みます。
- **停止。** **停止**は実行中と待機中のすべての実行を終わらせ、拡散モデルの描き直しも途中で打ち切ります。停止した実行は、それ以上何も書き込みません。
