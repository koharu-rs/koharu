ユーザーから見たスケジューリング、メモリ、レンダラーの動作については、[GPU で動くモデル](/ja/how-it-works/runtime)と[ページの描画](/ja/how-it-works/rendering)を参照してください。このページでは、実行を始めたりページを描いたりするコードが前提にしていることを説明します。

## 実行を依頼する

`koharu-pipeline` はリクエストを受け取ります。対象、工程の集合、必要ならその実行だけの設定です。アプリのボタン、キャンバス、エージェントは、どれもこの方法で実行を始めます。

| 対象                             | 工程                                            |
| -------------------------------- | ----------------------------------------------- |
| プロジェクト、または一部のページ | 検出、OCR、インペイント、翻訳の任意の組み合わせ |
| 一部のテキストブロック           | OCR、インペイント、翻訳                         |
| 塗った範囲                       | インペイント（プロンプトは任意）                |

- 実行できないリクエストはすぐに失敗します。工程がない、ブロックへの検出、範囲へのインペイント以外の工程、プロジェクトにないページやブロックです。
- 実行が伝えたことは起きた順に保持され、最後のイベントがどう終わったかを示すため、後から見た呼び出し元もすべてを見られます。
- 各実行はトレースされます。依頼したものの下に、キューに入ってから終わるまでのスパンと、実行中の各ページの工程ごとのスパンがあります。
- モデルを知っているのは工程だけです。各工程は、ページごとの結果を工程名のラベル付きの 1 つの取り消しステップとして書き込みます。

## フレームを求める

`koharu-renderer` は、開いているセッションのページを共有しやすい不変のフレームにし、GPU 上の vello で描きます。フレームはピクセルのほかに、各レイヤーが描いたもの、つまり範囲、表示されるかどうか、テキストの確定したレイアウト、1 つにまとめたマスク、PSD の書き出しが必要とするレイヤー単体のピクセルにも答えます。

テキストの大きさ、改行位置、配置は描画のたびに求められ、ほかの場所では求められません。ページの大きさを測る配置処理のように、それが必要なコードは独自に計算せずレンダラーに尋ねます。

<Note>
  キャンバス、PNG と PSD の書き出し、サムネイル、パイプラインの塗った範囲は、同じ GPU
  上の同じペインターで描かれるため、どの出力もエディターの表示と一致します。
</Note>

## ウィンドウに表示する

ウィンドウは自身のサーフェスに 3 つの層を描きます。ネイティブのキャンバス、その上に React のインターフェース、さらにその上に、開いた `<select>` などインターフェースが開くポップアップです。CEF はインターフェースをオフスクリーンで描画し、GPU が受け取れる場合は GPU テクスチャとして、そうでなければメモリ経由のコピーとして各描画を渡します。インターフェースが透明な場所ではページが見えます。

ポインターは、インターフェースが上に何も描いていない場所ではキャンバスへ、それ以外ではインターフェースへ送られます。キーは最後に押した側へ送られます。キャンバスを押した後はまずキャンバスへ送られ、キャンバスが使わないキーはインターフェースへ渡ります。`koharu-canvas` はポインターをジェスチャーに変え、オーバーレイでプレビューし、ほかの書き手と同じくデスクトップが適用する編集で応答します。

## デスクトップの結果を確認する

デバッグビルドは、独自のブラウザープロファイルで CEF の DevTools プロトコルを `http://127.0.0.1:4000` に公開します。インターフェースの確認と操作に使ってください。CDP のスクリーンショットにはインターフェースしか写らないため、キャンバスを含めた合成後のウィンドウは、デバッグビルドの `capture` コマンドで取得します。
